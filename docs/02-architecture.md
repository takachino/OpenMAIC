# アーキテクチャ

> 生成: OpenCode + DeepSeek V4.1 Flash Free（2026-11-02）

## 全体構成

OpenMAIC は Next.js の App Router を中心にした単一の Web アプリケーションです。
ブラウザ、アプリサーバー、PostgreSQL、外部のモデルプロバイダー、任意のレンダーサービスの 5 つで構成されます。

```
ブラウザ
  ├─ ホーム（/）                授業生成、教材ライブラリ、設定
  ├─ 教室（/classroom/[id]）    授業の再生、AI との対話
  ├─ ワークベンチ（/workbench） エージェントと共同でコースを構築
  └─ 管理・評価用ページ
        │  HTTP / SSE
        ▼
Next.js アプリ（Node.js 22）
  ├─ App Router のページと Route Handlers（app/api/*）
  ├─ 生成パイプライン（@openmaic/generation、lib/server/generation）
  ├─ 教室ディレクター（lib/chat/pi）
  ├─ エージェントランタイム（lib/server/agent-runtime）
  ├─ 再生エンジン（lib/playback）とアクションエンジン（lib/action）
  └─ 永続化層（@openmaic/storage、lib/persistence）
        │
        ├─ PostgreSQL 16        コース、履歴、学習者状態、素材、エージェントセッション
        ├─ アセットストア       PostgreSQL または S3 互換ストレージ
        ├─ モデルプロバイダー   LLM、画像、動画、TTS、ASR、検索、文書解析
        └─ render-service       Chromium + FFmpeg（MP4 書き出しとプレビュー、任意）
```

アプリサーバーは 1 つのプロセスである必要はありません。
生成ジョブとエージェントセッションは PostgreSQL のリース機構で排他され、複数プロセスで分担できます。

## リクエストの流れ

### 授業を生成する

1. ブラウザが `POST /api/generate-classroom` にテーマまたは資料を送る。
2. サーバーは生成ジョブを PostgreSQL のレコードとして登録し、すぐにジョブ ID を返す。
3. 各サーバープロセスのワーカーがジョブを拾い、チェックポイントを保存しながら段階的に進める。
   プロセスが落ちても、別のプロセスが最後のチェックポイントから引き継ぐ。
4. 構成案（アウトライン）ができると、設定に応じて確認待ちになる。
   学習者が内容を確認してからシーン生成へ進む。
5. アウトラインの各項目が `slide`、`quiz`、`interactive`、`pbl` のいずれかのシーンになる。
6. シーンごとに本文、アクション、ナレーション音声、画像・動画などの素材を生成する。
7. 完成したコースを PostgreSQL に保存し、素材をアセットストアに置く。
8. ブラウザはジョブの状態を購読し、完了すると教室の URL へ遷移する。

生成はサーバー側で進むため、ブラウザのタブを閉じても継続します。
ただし、そのためにはリクエストを超えて生き続ける Node.js プロセスが必要です。

### 教室を再生する

1. ブラウザが `/classroom/[id]` を開き、`/api/stages` からコースを取得する。
2. 再生エンジンがシーンの `actions` を順に解釈し、アクションエンジンに渡す。
3. 発話アクションは TTS で音声に変換され、字幕とともに再生される。
4. ホワイトボードやスポットライトのアクションは、描画と演出として実行される。
5. 議論や Q&A のターンでは、`/api/chat` に SSE で接続し、Pi がエージェントを呼び分ける。
6. 学習者の発言や操作は、学習者ランタイムの状態として保存される。

再生エンジンの状態は `idle`、`playing`、`paused`、`live` の 4 つです。
`live` は議論や対話のターンを表し、終了すると `playing` に戻ります。

## 生成パイプライン

生成は「アウトライン」と「シーン内容」の 2 段階です。

**アウトライン生成**では、入力されたテーマと資料をもとに、コースの目的、対象者、章立て、各ページの役割を決めます。
構成案は後から編集できるデータとして保持されます。

**シーン内容生成**では、アウトラインの各項目を具体的なシーンに変換します。
シーン種別ごとにプロンプトと検証が分かれ、スライドは要素の配置、クイズは問題と正答、インタラクティブは HTML と操作、PBL は役割とマイルストーンを生成します。

1.3.0 では、アップロードされた資料がナレッジベースに保存され、最初の添付時に一度だけ解析されます。
解析結果のテキストと画像は、その後の会話や生成で再利用されます。
PDF の解析には `unpdf`、MinerU、AliDocMind などを用途に応じて使い分けます。

## マルチエージェント

教室の進行は `lib/chat/pi/` のディレクターが担います。
ディレクターは教師役の 1 体ではなく、ターンごとに「誰に話させるか」を決める進行役です。

- `call_agent`：指定したエージェントに発話や描画を依頼する。
- `cue_user`：学習者に発言を促す。
- `read_scene`：現在のシーンの内容を参照する。
- `close_session`：対話を終了する。
- `web_search`：必要に応じて外部検索を行う。

エージェントの定義は `lib/orchestration/` のレジストリで管理します。
各エージェントはペルソナ、声、担当教科、参加できるモードを持ちます。

Pro ワークベンチのエージェントは、教室の進行役とは別のランタイムで動きます。
こちらは `lib/server/agent-runtime/` の耐久セッションを使い、コースの読み書き、素材の取り込み、画像・音声の生成、PPTX のインポートなどをツールとして実行します。

## データモデル

コースの構造は `packages/@openmaic/dsl` が定義します。
バージョン付きのデータ契約で、アプリ、レンダラー、インポーター、エディターが同じ型を共有します。

```
Stage（コース）
  ├─ メタ情報（タイトル、説明、言語、作成者、公開状態）
  └─ Scene[]（ページ）
       ├─ type: 'slide' | 'quiz' | 'interactive' | 'pbl'
       ├─ content: シーン種別ごとの内容
       └─ actions: Action[]（発話、描画、演出）
```

`Action` には発話、ホワイトボードの描画、テキスト、図形、グラフ、スポットライト、レーザーなどがあります。
再生エンジンは中間コンパイルを行わず、`actions` をそのまま実行します。

## 永続化

`@openmaic/storage` は、用途ごとに交換可能なストアを定義します。

| ストア | 内容 |
| --- | --- |
| DocumentStore | コース、フォルダ、シーン |
| RuntimeStore | 学習者の進行状態、再生位置 |
| KvStore | 端末に紐づく設定値 |
| AssetStore | 画像、音声、動画などのバイト列 |
| AgentSessionStore | エージェントのセッション、イベント、リース |
| MaterialStore | アップロード資料と解析結果 |
| SkillStore | ユーザーが作成したスキル |

サーバー側の実装は PostgreSQL が基準です。
アセットのバイト列は PostgreSQL に置くことも、S3 互換ストレージに置くこともできます。
ブラウザは `/api/persistence` の HTTP 契約を通じてサーバーに接続します。

コースの読み取りはステージ ID を能力として扱いますが、書き込みはオーナーに限定されます。
オーナーの解決方法は 4 つあり、詳細は [03-setup.md](03-setup.md#オーナーとアクセス制御) にあります。

## モデル解決

モデル設定は `openmaic.yml` の `providers` と `slots` で行います。

- **providers**：サーバーが呼べるアカウントを定義する。プリセット、API キー、ベース URL、許可するモデルを書く。
- **slots**：AI の用途ごとに、使うプロバイダーとモデルを割り当てる。未設定のスロットは親スロットを継承する。
- **lock**：利用者が変更できないスロットを固定する。
- **allowUserKeys**：利用者が自分のプロバイダーやキーを追加できるかを決める。

スロットは能力ごとの木構造です。
たとえば `course.content.slide` は `course.content` を継承し、`course.content` は `llm` を継承します。
`agent` スロットだけはツール呼び出しが必要で、`thinking.effort` を設定できません。

サーバー管理のプロバイダーでは、`models` が許可リストとして機能します。
設定にないモデルは、たとえ SDK のカタログに存在しても、サーバーの費用では使えません。
解決できないモデルは推測せず、起動時または呼び出し時に明示的に失敗します。

## セキュリティ境界

- **URL ガード**：利用者が指定した URL へのサーバー側リクエストは、SSRF ガードを通す。
  リダイレクトの検証、プライベートアドレスの拒否、既知のクラウドメタデータエンドポイントの遮断を行う。
- **資格情報の隔離**：プロバイダーのキーはサーバーに留め、ブラウザへ渡さない。
- **機能の強制無効化**：`<CAP>_<PREFIX>_ENABLED=false` で、特定の能力をデプロイ全体で無効にできる。
- **ACCESS_CODE**：サイト全体のパスワード。未設定の場合はミドルウェアが認証を行わない。
- **インスタンス秘密鍵**：`OPENMAIC_SECRET_KEY` は、画面から保存したプロバイダーキーの暗号化に使う。
  データベースと一緒に保管する。

## 設計上のトレードオフ

**サーバー主体にした代償**：生成の継続性とデータの一元管理を得る代わりに、PostgreSQL と長時間稼働するプロセスが必須になりました。
サーバーレス環境では動かないため、デプロイ先の選択肢は狭くなります。

**プロバイダー非依存にした代償**：特定ベンダーの便利な機能をそのまま使うのではなく、共通の能力インターフェースに合わせる必要があります。
そのぶん、モデルを差し替えても製品側のコードを変えずに済みます。

**オーナー分離にした代償**：すべての読み書きにオーナーの解決が必要になり、デプロイモードの選択が導入時の判断事項になります。
一方で、匿名ブラウザからチーム共有までを同じコードで扱えます。
